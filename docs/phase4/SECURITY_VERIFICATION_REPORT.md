# Security verification report (Phase 4.1)

**Scope and limits.** An independent re-audit of the Phase 4 security work, done by a fresh inventory of the code rather than by trusting the Phase 4 audit. Tested only on an isolated local instance (`php -S` and Apache 2.4 + mod_php, MariaDB test database, local SMTP sink, synthetic data). No production, staging, hosting, DNS, SSL, credential or live-database access. **Git history was not modified.** Not covered: third-party penetration testing, real proxy/CDN behaviour, real mail, nginx/LiteSpeed rules, the `vendor/` (PHPMailer) dependency audit, denial-of-service load.

## 1. Method
1. **Endpoint manifest** (`tests/security_manifest.json`): every one of the 106 top-level PHP files is classified (56 public pages, 20 include-only libraries, 9 CLI maintenance scripts, 6 write endpoints, 4 token endpoints, 2 admin pages, 4 demo pages, 3 redirects, 2 retired). `tests/security_inventory_test.php` fails for any unclassified file and enforces the rules of each kind (guards present, no sinks in pages, admin gate before output, demo gating, CLI guard, safe redirects, no dangerous functions, no debug switches).
2. **Secrets and personal data scan** of all 543 tracked files for private keys, cloud/API tokens, SMTP app passwords, the known leaked database password, literal credential assignments, key/backup files, SQL dumps with personal data, and email addresses in visitor-generated data. The scanner was itself tested by planting fake secrets in a tracked file (it flagged all three).
3. **Negative HTTP suite** (`tests/security_negative_http_test.php`, 123 checks): a barrage of 18 hostile requests per endpoint (SQL/XSS/traversal/CRLF/oversize values in 27 parameter names; GET, POST, JSON, PUT, DELETE, PATCH; about 1,300 requests) with a before/after snapshot of every database table and data file; plus targeted tests listed below.
4. **Apache validation**: the same suites run against a real Apache 2.4 + mod_php using the repository's `.htaccess` (this found issues `php -S` hides).
5. Earlier suites kept: `tests/security_test.php` (147), `tests/security_http_test.php` (75).

## 4. Negative test inventory (what a regression would break)
`tests/security_negative_http_test.php` sections: never-reachable files (libraries, CLI scripts, extensions, dotfiles, docs, vendor); hostile barrage with state snapshot; path traversal on 11 content endpoints; Host-header poisoning (page URLs and email links); forms (mass assignment, 9 rejection cases, time trap, oversize, SQL/XSS payloads); spoofed forwarding headers vs DB rate limits; admin access matrix, brute-force lockout, SQLi passwords, session fixation; outbound redirect and click inflation; prefetch-safe newsletter confirmation.
`tests/security_inventory_test.php` sections: manifest classification, per-kind rules, redirect hygiene, dangerous functions/debug switches, secrets and personal data in tracked files.

## 5. Residual risks (honest list)
- **R1 Anonymous endpoints use stateless tokens, honeypots and limits, not identity.** A determined attacker with many IP addresses can still submit comments or leads at the rate-limit pace; moderation exists only for comments/leads you read.
- **R2 Rate limiting is file-based per server.** On several servers or an ephemeral filesystem, limits reset or diverge. A shared store is recommended before scaling out.
- **R3 Trusted-proxy configuration is mandatory in front of a CDN**, otherwise all visitors share one rate-limit identity (fails safe but noisy).
- **R4 Secrets in history** until you rotate (and optionally purge). Every existing branch, including `main`, still has them.
- **R5 No CSP**; pages still use inline styles/scripts. HSTS, TLS, security headers at the edge are manual.
- **R6 Dependencies** (`vendor/` PHPMailer) not audited; no composer audit was possible offline.
- **R7 JSON data files** (comments, ratings, votes) are writable by PHP and unauthenticated; they are escaped on output and rate limited but not moderated.
- **R8 nginx/LiteSpeed**: the `.htaccess` rules are verified only on Apache; the in-code guards cover the libraries but not `data/`, `docs/`, `vendor/` or dotfiles on other servers (manual checklist item).
- **R9 No third-party penetration test** and no real mail/proxy testing.
